================================
FLUJO DE REGISTRO
================================

1. Usuario envía datos de registro al backend
   POST /api/auth/register
   {
     "tipo_documento": "CC",
     "numero_documento": "123456",
     "nombres": "Juan",
     "apellidos": "Pérez",
     "correo": "juan@email.com",
     "usuario": "juanperez",
     "contrasena": "Pass123!",
     "rol_nombre": "paciente"
   }

2. Backend (authController.register):
   a) Valida datos
   b) Verifica que documento/correo/usuario no existan (Supabase)
   c) Inserta en tabla `personas` (Supabase)
   d) Hashea contraseña con bcrypt
   e) Inserta en tabla `credenciales` (Supabase)
   f) OPCIONAL: Crea usuario en Firebase Auth
   g) Establece custom claims en Firebase
   h) Retorna datos del usuario

3. Usuario creado en:
   ✅ Supabase: persona + credencial
   ✅ Firebase: usuario con email/password + custom claims

================================
FLUJO DE LOGIN
================================

1. Usuario envía credenciales al backend
   POST /api/auth/login
   {
     "usuario": "juanperez",
     "contrasena": "Pass123!"
   }

2. Backend (authController.login):
   a) Busca usuario en tabla `credenciales` (Supabase)
   b) Verifica contraseña con bcrypt
   c) Si válido, obtiene datos de `personas` (Supabase)
   d) Si tiene firebase_uid, genera custom token (Firebase)
   e) Establece cookie con token
   f) Retorna datos del usuario + token

3. Usuario recibe:
   {
     "success": true,
     "customToken": "firebase-token...",
     "user": { ... }
   }

================================
FLUJO DE REQUEST PROTEGIDO
================================

1. Usuario hace request con token
   GET /api/personas/123
   Cookie: authToken=firebase-custom-token
   O
   Header: Authorization: Bearer firebase-custom-token

2. Middleware (authMiddleware.verifyToken):
   a) Extrae token de cookie o header
   b) Verifica token con Firebase Admin SDK
   c) Decodifica token y obtiene uid, rol, email
   d) Agrega req.user = { uid, email, rol }
   e) Continúa al siguiente middleware/controlador

3. Controlador ejecuta lógica:
   a) Usa req.user.uid para identificar usuario
   b) Consulta Supabase para datos
   c) Retorna respuesta

================================
SEPARACIÓN DE RESPONSABILIDADES
================================

FIREBASE:
✅ Autenticación (tokens JWT)
✅ Verificación de identidad
✅ Gestión de sesiones
✅ Custom claims (roles)
❌ NO almacena datos de negocio
❌ NO guarda información médica
❌ NO gestiona citas/documentos

SUPABASE:
✅ Almacenamiento de datos
✅ Queries SQL complejas
✅ Relaciones entre tablas
✅ Constraints y validaciones
✅ Transacciones ACID
✅ Backups automáticos
❌ NO maneja autenticación
❌ NO genera tokens JWT

================================
VENTAJAS DE ESTA ARQUITECTURA
================================

1. ESCALABILIDAD
   - Firebase maneja millones de autenticaciones
   - Supabase escala PostgreSQL automáticamente

2. SEGURIDAD
   - Tokens JWT seguros de Firebase
   - Datos sensibles en PostgreSQL con SSL
   - Separación de preocupaciones

3. DESARROLLO
   - Dashboard visual de Supabase
   - Console de Firebase para auth
   - SQL completo para queries complejas
   - Triggers y stored procedures disponibles

4. COSTO
   - Firebase: Plan gratuito para auth
   - Supabase: 500MB gratis de base de datos
   - Escala según necesidad

5. FLEXIBILIDAD
   - Puedes cambiar Firebase por otro servicio
   - Puedes cambiar Supabase por otro PostgreSQL
   - Backend desacoplado de servicios externos

================================
FLUJO DE DATOS COMPLETO
================================

REGISTRO:
Frontend → Backend → Supabase (INSERT) → Firebase (createUser) → Response

LOGIN:
Frontend → Backend → Supabase (SELECT) → Firebase (verifyPassword) → Firebase (customToken) → Response

CONSULTA:
Frontend → Backend → Firebase (verifyToken) → Supabase (SELECT) → Response

CREAR CITA:
Frontend → Backend → Firebase (verifyToken) → Supabase (INSERT con validaciones FK) → Response
